status of the iPhone + Xiaomi Smart Band 10 behavior must still be recorded by

## Preconditions and install

1. Use an iPhone running iOS 17 or later and a Xiaomi Smart Band 10 on the
   current test firmware. Record the observed firmware version.
2. Close Mi Fitness before connecting directly. Keep the phone stationary for
   the first route start; a passenger or stationary tester observes the Band
   during any movement test.
3. Install the IPA and RPK from this bundle. Verify `SHA256SUMS` before
   installation. Do not reuse the old H1 artifact directory.
4. Open Config and save AuthKey, Vietmap Route/service key, Vietmap TileMap
   key, and a destination latitude/longitude. Never include these secrets in
   screenshots, exports or bug reports.

## Test script

Record a local timestamp, iPhone/iOS, Band firmware, artifact hashes and the
result of every row. A test result is `PASS-HW`, `FAIL-HW`, `BLOCKED-ENV`, or
`NEEDS-MEASURE`; automated CI is not a hardware result.

### A. Pairing and first route

1. Open the app, scan and select the Band, then complete authentication, TOFU
   trust and RPK readiness. Expected: the app reaches `applicationReady`, the
   Band stays responsive, and no secrets are logged.
2. Start navigation with a real destination. Expected: the app makes one
   Vietmap Route v4 motorcycle request, receives a valid route, and shows a
   route preview before asset transfer. A provider error must stop navigation;
   it must not show mock coordinates.
   If start fails, record the visible error code, open `Debug log`, and use
   `Export debug log`. The export must contain the start/destination summary,
   route response or failure stage, and each decoded instruction while keeping
   service keys, UUIDs and full-precision coordinates out of the report.
3. Compare the Band image with the iPhone preview carrying the same `scene`.
   Expected: a continuous cyan route, selected gray side roads, a visible
   maneuver point, a moving native marker, and the correct arrow/distance.

### B. Five-start performance gate

4. Repeat route start five times from a clean connected session. Record frame
   time, PNG bytes and data-chunk count for each run. Every run must have a
   useful real route frame within 5 seconds at p95, PNG `<= 1,024` bytes and
   no more than 7 data chunks. ACK wait is allowed to be measured separately.

### C. Navigation behavior

5. Exercise fixtures/routes containing `straight`, `left`, `right`, `uTurn`,
   `roundabout` and `arrive`. Expected: the next maneuver and distance are
   recognizable within 2 seconds in at least 4 of 5 observations; route
   geometry stays continuous and the marker uses `x/y` without rotating roads.
6. Observe live updates while walking/driving only with a passenger. Expected:
   `nav.update` reaches the Band at no more than 1 Hz, latest data replaces a
   queued stale update, and the marker follows progress monotonically.
7. Attenuate or block GPS for several good-looking fixes. Expected: status is
   `GPS LOW`, the last good marker/progress is held, and no synthetic position
   appears.
8. After Route v4 succeeds, deny TileMap style/tile access. Expected:
   route-only rendering remains usable and status is `LIMITED MAP`.
9. Leave the route for three consecutive good GPS fixes. Expected: exactly one
   reroute after the 15-second cooldown, with status `REROUTING`; no repeated
   request storm. Move within 25 m of the destination. Expected: `ARRIVED`.

### D. Session safety and stability

10. Disconnect during asset transfer and again during live updates, then
    reconnect. Expected: partial ownership is cleared, stale scene/sequence
    messages are ignored, and the next run starts normally.
11. Run for 30 minutes with the Band visible. Expected: no freeze, black
    screen, reboot, or unexpected Mi Fitness takeover.

Stop immediately for a freeze, black screen, reboot, corrupted route geometry,
wrong maneuver, stale update replacing a current scene, or any secret shown in
diagnostics. Do not operate the phone or Band while controlling a motorcycle.

## Evidence to return

- One sanitized result table with the first failing step, if any.
- Five-start timing/bytes/chunks measurements and the observed ACK p95.
- Safe screenshots of the iPhone preview and Band for matching `scene` values.
- Firmware/OS/app/RPK versions and sanitized error codes only.
- Vietmap request count (Route v4 and style/tile separately), never keys or
  effective URLs.

Do not return AuthKey, Vietmap keys, CoreBluetooth identifiers, nonces, HMACs,
derived keys, raw encrypted payloads, raw BLE captures, provisioning profiles
or private signing material.
